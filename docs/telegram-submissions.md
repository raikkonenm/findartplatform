# Private FINDART submission drafts

This is a separate, disabled-by-default intake pipeline for the existing `@FINDART_content_bot`. It does not publish submissions to the website, deploy the site, alter exhibition records, or enable the existing published-content automation.

## Website forms: primary email plus Telegram

The existing `/api/submissions` handler continues to send through Resend to **raikkonenmaria7@gmail.com**. With `SUBMISSIONS_CAPTURE_ENABLED=true`, it also saves a private queue item after successful email delivery. No Gmail connection, ChatGPT Gmail plugin, extra recipient mailbox, or always-on personal computer is needed for these forms.

| Existing form | Intake type | Existing behavior preserved |
| --- | --- | --- |
| Exhibition | `exhibition` | Email, then existing Gumroad redirect |
| Artist | `artist` | Email, then existing Gumroad redirect |
| Editorial / Article | `contribute` | Email, free form success |
| Opportunities | `opportunity` | Email, then existing Gumroad redirect |
| Website / Index | `index` | Email, then existing Gumroad redirect |

Contact and Advertising are outside this intake. A Gumroad redirect does not prove payment: paid-form drafts show **Not verified**. Editorial is marked free only when its actual form type is `contribute`.

A signed receipt correlates the email copy with the direct event. The queue deduplicates source IDs and matching canonical form/email payloads within seven days. A later deliberate resubmission may be a new job. If private storage is unavailable after email succeeds, the form still succeeds and the server logs only `FINDART_SUBMISSION_CAPTURE_FAILED_EMAIL_FALLBACK`. The original email remains available for manual recovery; automatic email recovery requires the separately enabled Gmail adapter. Monitor this fixed error code before enabling capture.

## Cloud services and permissions

1. Create a dedicated Supabase project for private submissions. Apply [supabase/submissions.sql](../supabase/submissions.sql) in its SQL editor after review. The migration creates the queue, source IDs, cursors and **private** `findart-submissions-private` bucket. Tables deny anonymous and signed-in user access; only the server service role may use the RPCs and objects. The migration refuses a bucket that is already public. Do not create public bucket policies or download URLs.
2. On the development website server, configure `SUBMISSIONS_SUPABASE_URL`, `SUBMISSIONS_SUPABASE_SECRET_KEY` and a randomly generated `SUBMISSIONS_HMAC_KEY` of at least 32 characters. Use a modern server-only `sb_secret_` key from Supabase Settings → API Keys, not a publishable key. Legacy `SUBMISSIONS_SUPABASE_SERVICE_ROLE_KEY` remains a compatibility fallback; the new key uses `apikey` without an invalid JWT bearer header. Keep the existing Resend configuration and recipient. Leave `SUBMISSIONS_CAPTURE_ENABLED=false` until review. None of these values belongs in `NEXT_PUBLIC_*`, committed files, chat messages or browser code.
3. In repository **Settings → Secrets and variables → Actions**, add the same three values as repository secrets, plus `OPENAI_API_KEY`. Configure `SUBMISSIONS_OPENAI_MODEL` as a variable naming a model that supports Responses Structured Outputs. Reuse the already configured `TELEGRAM_BOT_TOKEN` and personal `TELEGRAM_CHAT_ID`; do not create another bot. The worker verifies the bot username and exact private chat with `getMe` and `getChat` before sending.
4. Leave repository variable `TELEGRAM_SUBMISSIONS_ENABLED=false`. Leave `GMAIL_SUBMISSIONS_ENABLED=false`. `TELEGRAM_SUBMISSIONS_MANUAL_ENABLED=true` permits only an explicitly selected test UUID; it does not enable the queue. The published-content `TELEGRAM_DELIVERY_ENABLED` is independent and remains off. The submission worker needs only `contents: read`, **no Issue permissions**. It never reads or writes Issue #1. No `VERCEL_PROJECT_ID` or `TELEGRAM_STATE_ISSUE` is needed by the private submission worker.

The source is intended for a dedicated private store even when the code repository is public. Service-role credentials bypass Supabase RLS: protect them as server-only secrets. Rotate credentials through their service and secret settings, never through committed configuration. Supabase retention/backup and cleanup policies must be chosen by the account owner; no automatic deletion of application materials is included.

## Optional email-only submissions

This is needed only for applications sent as email instead of using the website forms. **Connecting Gmail to ChatGPT does not configure the cloud worker.** Its OAuth permission is separate and can be granted in the user's own browser without anyone controlling their computer.

Create a Google Cloud OAuth client with Gmail API enabled. Authorize only `https://www.googleapis.com/auth/gmail.readonly` with offline access for the intended mailbox. The optional local `node scripts/submissions/google-oauth.mjs` helper displays the consent link, receives the localhost callback and saves the refresh token only to ignored `.submission-delivery/oauth/gmail-token.json`. Supply `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` through the local environment; the helper does not print tokens. Move the resulting token directly into an Actions secret, then remove the local token file when no longer needed. Google consent/testing restrictions and refresh-token lifetime must be resolved in the Google Cloud project before unattended use.

Required optional Actions secrets:

- `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`.
- `GMAIL_SUBMISSIONS_ADDRESS`: the exact authorized mailbox, verified against Gmail's profile before polling.
- `GMAIL_SUBMISSIONS_QUERY`: a narrow query containing a dedicated label, for example `label:FINDART-Submissions`. Create a Gmail filter applying that label only to relevant submissions. Never use a whole-inbox query.

Set `GMAIL_SUBMISSIONS_START_AFTER` as an ISO date/time variable for the agreed activation time. This prevents historical backfill; polling uses bounded pages and a private cursor. Enable `GMAIL_SUBMISSIONS_ENABLED` only after approval. The adapter uses read-only GET requests; it never marks read, modifies labels, deletes or sends mail. Signed website copies deduplicate against direct capture.

## Editorial and media processing

The worker obtains applicant-provided attachments and links, extracts text from PDF, DOCX, TXT/HTML and bounded ZIPs, and optionally reads document scans with Tesseract. It does not execute applicant code, scripts, macros or instructions. Missing OCR, unreadable/encrypted documents and inaccessible links appear as review notices in the private administrative card.

OpenAI Responses receives the application materials for extraction and English editorial drafting with `store:false`, no command/browsing tools and a strict JSON schema. This still transmits the materials to OpenAI for processing. Factual values must carry exact source evidence. Missing credits, uncertain accounts, unavailable Latin spellings and conflicting information require review. AI summaries remain unquoted; English quotations must occur verbatim in a real source. Incoming-submission captions use a continuous **5–10 sentence passage**, preferring 5–7 when needed to reserve every supported credit within 2,200 characters; shorter sources are disclosed. Published-content exports retain their separate seven-sentence default. Every package is marked **EDITORIAL DRAFT — NOT APPROVED** and remains subject to human editorial review. Applicant email appears only in private administrative/original material, not the Instagram caption.

Download support and explicit limits:

- Public Google Drive file links; public Drive folders require optional `GOOGLE_DRIVE_API_KEY`. Folder traversal is bounded and filenames sorted naturally when no authoritative order is supplied. Private/confirmation pages require manual access.
- Public Dropbox download links and folder ZIPs.
- Direct downloadable WeTransfer/CDN files. **Interactive WeTransfer shared pages requiring JavaScript, login, a password or access confirmation are not automatically resolved.** They are reported honestly with their original link; no images are invented or substituted.
- Other HTTPS download hosts only through explicitly approved `SUBMISSIONS_DOWNLOAD_HOSTS` (comma-separated exact hosts or subdomain patterns). Website/portfolio pages are not scraped indiscriminately for replacement images.
- Downloads: 49 MB/file, 250 MB total, 200 files, 30 source links, five redirects, public-IP checks and pinned DNS. Archive paths, links, encryption, entry count, expansion ratio and nested depth are checked. Oversized files require review rather than silent shrinking.

Provided image order is preserved; duplicate bytes and technical icons/logos/thumbnails are excluded. The existing JPEG exporter copies original JPEG bytes unchanged, converts other supported photo formats at quality 95, 4:4:4, sRGB without resizing, and changes extensions to `.jpg`. Original website images are untouched. Each JPEG uses `sendDocument`, never compressed Telegram photos. ZIP parts contain the exact exported JPEG bytes and fit the existing upload limit.

Dropbox ZIPs may contain a zero-byte `/` directory marker. This one metadata entry is ignored without extracting any absolute path; absolute file entries, traversal, links and encrypted entries remain blocked. For multi-location exhibitions, extract each separately dated presentation with its own evidenced title, city and date range. Combining them requires an evidenced `eventRelationship: chapters`, explicitly supported by the source's description of chapters/parts of one exhibition. A common artist, gallery or press release alone is insufficient. Independent or unclear events are held for separate editorial review, never combined into one caption. Preserve each chapter's opening date in both the administrative card and editorial credits; do not apply one city's date to every location. Unparseable date wording remains visible for review rather than being silently discarded.

Delivery order is the administrative card, English editorial text, caption TXT, original submission TXT, JPEG documents, then JPEG ZIP part(s). All documents have the draft label as their Telegram caption. The caption TXT contains copy-ready editorial text and has `EDITORIAL-DRAFT` in its filename. The private administrative card includes the requested submission fields, original source reference, all available download links, warnings and actual obtained-image count.

## Checkpoints and recovery

Jobs and file receipts stay in private Supabase tables; prepared files stay in the private bucket. Downloaded originals, ZIPs and documents are cached privately **before** the AI request. A transient AI failure reuses hash-checked cached originals instead of relying on expiring external links. Local dry-runs stay in ignored `.submission-delivery/`. The workflow prints aggregate counts and fixed error codes only: no applicant payloads, captions, emails, URLs, draft artifacts or issue comments.

The database leases a job to one worker; each Telegram step is saved **before** the request and its receipt saved before proceeding. Successful steps are skipped on resume. Explicit rejections have bounded retries; a lost response/in-flight step becomes private review and is never automatically resent. File hashes and Telegram-returned names/sizes are checked. Inspect the bot and private checkpoint before resolving an uncertain step; do not wipe progress or bypass duplicate detection. Review/error jobs are not automatically claimed again. Storage/AI failures also require private review, with already-written delivery checkpoints preserved.

The scheduled workflow processes at most two jobs per run and shares the existing Telegram transport lock without sharing published-content state. It is cloud-hosted, so the user's computer can be off. GitHub scheduled runs are best-effort, can be delayed, and run only from the default branch. Public-repository scheduled workflows may be disabled after 60 days without activity. The prepared Vercel integration addresses this without another server: a captured form can wake the workflow immediately, and a daily protected Vercel Cron acts as a watchdog. It re-enables only `disabled_inactivity`, respects `disabled_manually`, and dispatches without applicant data. Daily cron fits Vercel Hobby; no paid Vercel upgrade is required for that schedule. The wake path is gated by `SUBMISSIONS_WORKER_WAKE_ENABLED=true` **and** `VERCEL_ENV=production`; both capture and wake remain disabled until approved. A branch-only implementation cannot collect production form events until the approved backend/configuration is deployed; this task does **not** perform that deployment.

## Review before activation

All automatic switches remain false; the independent manual switch authorizes a single selected test. The current implementation can be tested without sending anything:

```sh
python -m pip install -r scripts/submissions/requirements.txt
npm run test:telegram
npm run test:submissions
npm run submissions:dry-run -- --input .submission-delivery/example.json
npm run submissions:connections
```

`example.json` is a private normalized application object with `type`, `fields`, `originalText`, `source` and optional `attachments`/`links`. For an actual historical Gmail message, normalize its full API response with `normaliseGmail` first; do not put it in a workflow input. For a one-time offline human-reviewed analysis, the dry-run also accepts `--reviewed-analysis .submission-delivery/analysis.json` matching the extraction schema. Live execution never accepts that override.

Open the generated private `draft-package.json`, exact caption TXT and ordered JPEG inventory. Show the actual English caption, sentence/character counts, obtained-image count and planned steps to the owner. A synthetic fixture is a code test, **not** a completed real-application dry-run. Obtain approval for the real example and activation separately; never mass-send old applications. Website production deployment and enabling the production capture flag also require the owner's authorization.

The synthetic CI installs PGlite only for tests and requires the real PostgreSQL migration/permission/checkpoint test to run. Local tests skip that single test if PGlite is unavailable; do not report it as passed. The tests also cover all five form contracts, unchanged primary email delivery, direct delivery without Gmail, source evidence, private email exclusion, inaccessible links, JPEG/ZIP preparation, untrusted ZIP/XML inputs, duplicate input and partial/uncertain delivery.

## Account setup and controlled cloud test

No subscription or paid project is created automatically. These are the owner-controlled account steps; keys must be entered in service secret settings, never chat.

1. **Private storage:** open [Supabase Dashboard](https://supabase.com/dashboard), select an existing suitable project or create one. Free is sufficient for the initial test, but includes only 1 GB storage and can pause after one week of inactivity. For unattended production, Supabase Pro currently starts at $25/month for one project; review billing before upgrading. See [pricing](https://supabase.com/pricing). Connect the project so the migration and checks can be performed, or apply the reviewed SQL in its SQL editor. In Settings → API Keys create a server secret key; obtain the project URL from Connect. Save the URL and server key under the names above in [GitHub Actions secrets](https://github.com/raikkonenm/findartplatform/settings/secrets/actions). Original and exported media consume storage; large histories need an owner-approved retention policy.
2. **AI:** create a project key at [OpenAI API keys](https://platform.openai.com/api-keys), with Responses generation access. Configure billing/credits in [API billing](https://platform.openai.com/settings/organization/billing/overview) if required. Save it as `OPENAI_API_KEY` in GitHub Secrets. The configured model variable is `gpt-5.4-mini-2026-03-17`. Standard rates checked on 30 October 2026 are $0.75/1M input tokens and $4.50/1M output tokens. Example: 20,000 input + 4,000 output tokens = **$0.033 per application**. Larger documents, reasoning and retries can increase this. No external browsing, image generation or image-analysis API charges are added by this pipeline. Sources: [model pricing](https://developers.openai.com/api/docs/models/gpt-5.4-mini), [API quickstart](https://developers.openai.com/api/docs/quickstart).
3. **Shared receipt key:** generate a cryptographically random `SUBMISSIONS_HMAC_KEY` of at least 32 characters. Use the same value in GitHub Secrets and the Vercel server environment so direct events and their email copies match. It is not an API key and incurs no cost. Provision it through secure environment/secret tooling; never commit or print it.
4. **Existing Vercel project:** the deployment metadata identifies [FindArt's Vercel project](https://vercel.com/maria-raikkonen-s-projects/findartplatform). Connect it for environment setup. The form server needs the three storage/receipt settings, the unchanged Resend settings, and initially `SUBMISSIONS_CAPTURE_ENABLED=false`. The worker's OpenAI and Telegram credentials belong in Actions, not the website browser.
5. **Daily watchdog/on-demand wake:** at [GitHub fine-grained tokens](https://github.com/settings/personal-access-tokens/new), create a token restricted to `raikkonenm/findartplatform`, with **Actions: Read and write** and the default Metadata access. No contents or Issues write permission is needed. Store it in Vercel only as `SUBMISSIONS_GITHUB_ACTIONS_TOKEN`. Set a separate random `CRON_SECRET` of at least 32 characters in Vercel. Keep `SUBMISSIONS_WORKER_WAKE_ENABLED=false`. The code/configuration must reach the approved default branch and production deployment before Vercel's daily cron can operate. Do not set wake/capture flags just to test Telegram. References: [GitHub workflow permissions](https://docs.github.com/en/rest/actions/workflows), [Vercel cron auth](https://vercel.com/docs/cron-jobs/manage-cron-jobs), [Hobby schedule limits](https://vercel.com/docs/cron-jobs/usage-and-pricing).
6. **Email-only source:** open [Google Cloud Console](https://console.cloud.google.com/), create/select a project, enable Gmail API, configure Google Auth Platform consent, and create your own OAuth client. Authorize the exact submission mailbox for `gmail.readonly` and offline access. The local helper above supports a Desktop application client. Alternatively, for a browser-only setup use a Web application client with authorized redirect `https://developers.google.com/oauthplayground`, then [Google OAuth Playground](https://developers.google.com/oauthplayground/) → settings → Use your own OAuth credentials → the `gmail.readonly` scope → Authorize APIs → Exchange authorization code for tokens. Use offline access. Save the client ID/secret and refresh token directly into their GitHub Secrets. Playground's shared default OAuth client is unsuitable for a persistent connection. External consent apps in Testing can issue refresh tokens expiring after seven days; use a permitted Production consent configuration for unattended operation and resolve any Google verification/account policy requirements. See [Google token expiration rules](https://developers.google.com/identity/protocols/oauth2#expiration). Create the narrow mailbox label/filter and activation timestamp described above; leave polling off until approval.
7. **Probe, then one test:** the `Private submission connection checks` workflow tests the exact private bot chat, Supabase RLS/RPC grants, private bucket write/read plus denied public access, and a tiny Structured Outputs request. It never sends content or polls the inbox. Reports contain booleans/states/token counts only. `coreReady` covers storage, HMAC, bot and AI; `allSourcesReady` additionally requires the filtered Gmail source. Missing settings are a configuration block, not successful connectivity.
8. **Private test intake:** with server secrets available securely, run `npm run submissions:enqueue-test -- .submission-delivery/example.json`, or enqueue the equivalent reviewed payload through the connected private database. Only the returned opaque UUID may appear in an Actions input. Do not upload the email, private links or photographs as GitHub artifacts/committed fixtures. The test job must be pending and use the real source payload so cloud AI preparation is exercised, not a prefilled offline analysis.
9. **One controlled send:** dispatch `Private submission drafts` with that `test_job_id`. The worker requires `TELEGRAM_SUBMISSIONS_MANUAL_ENABLED=true`, skips Gmail, leases only that UUID and processes at most one job, even if other work is pending. It checks core connections before sending. The final private summary verifies that every expected document has a Telegram receipt, with no uncertain step. JPEG receipts must report `image/jpeg`, the expected filename and exact size. Reusing the same UUID resumes confirmed checkpoints; completed jobs do not resend. A branch-only workflow may need default-branch registration before manual dispatch; do not merge/deploy without the owner's authorization.
10. **Separate activation approval:** only after the single test succeeds and the owner separately approves future automation, set the agreed new-mail start time, enable the Gmail source and submission delivery, and enable approved production capture/wake flags. Do not queue or scan historical applications. Keep the independent published-content delivery setting unchanged. Never publish incoming drafts automatically.
